# AutoDL 控制台操作手册

适用于 `reference/console.js` 第 10 版。贴进页面的是它去掉注释与缩进的那一份 `reference/console.min.js`（函数文本 34095 字节，SHA-256 `12350addfdfd6bd880179d9d8b51089c642ccc26d3fb590a22667dd866008f85`）。这一份里没有克隆实例才用的那一段，其余代码逐行相同；要读脚本的代码看 `console.js`，贴的时候用 `console.min.js`。克隆实例时换贴带着那一段的 `reference/console-clone.min.js`，做法在 `reference/clone.md`。控制台上的按钮一律由这个页面脚本核对后再点。浏览器工具只用来打开和刷新页面、设视口、截小图让页面出帧、在定时选择器里打字，以及读主页（余额与提醒）和扣费页。任何原文、按钮或页面结构与本手册对不上，就停下告诉用户，不猜，也不换别的办法去点。

下文的 `ctl` 指本 skill 的 `scripts/ctl`，调用方式见 SKILL.md；"实例ID"指这台实例在控制台里的 ID，形如 `abcd123456-1234abcd`。

实测情况。2026-09-29 到 10-02 在一台测试实例上、内置浏览器的面板一直隐藏的情况下，用页面脚本走通过这些：读实例行；无卡开机（展开"更多"菜单、点"无卡模式开机"、绑定确认框、最终确认、结算为 `confirmed`）；实例关着时设定时关机（往选择器里打字、点两个"确定"、提示"设置成功"），带着定时开机，开机之后取消，以及关机之后取消还挂着的定时（提示"取消成功"）；已有定时时打开"修改"；读出关机确认框的原文后放弃；刷新之后用短模板取回脚本。有卡开机（"开机"按钮、绑定确认框、最终确认、结算）10-02 也用页面脚本走通过。菜单、确认框与对话框都要截两三次小图才显示完整。2026-10-06 第 10 版在真实页面上整份贴过一次、刷新后用短模板取回过三次，无卡开机与定时关机的设置、修改、取消都走通过。还没试过的有关机确认框的最终确认（这一版不放行）与 Claude in Chrome 下的情况。遇到与本手册不符的地方，按第 14 节停下。

第 13 节（控制台关机）、第 15 节（原文与结构备查）、第 16 节（没有浏览器工具时）与第 17 节（接手已经开着的实例）在 `reference/console-more.md`，节号不变，用到时再读。

## 1. 基本规则

1. 点击只由 `console.js` 做。它只有固定的几种操作，每次先核对页面、行、按钮与对话框再点；核对不过就返回 `{ok: false, refused: 原因}`，这时什么都没点。不要用浏览器工具的点击、按坐标点或别的脚本去点控制台上的任何东西。
2. 一次只做一个操作。操作在 `dismiss` 成功或 `settle` 返回 `confirmed` 时结束；别的情况下，只有刷新页面才能开始下一个。
3. 最终确认（`confirm` 或 `confirmTimerDialog`）一经调用，这次动作就算已尝试。之后只用 `settle` 只读核对，不为同一个目的再开始一次，直到按第 9 节查明结果。
4. 刷新页面会丢掉脚本和进行中的操作。最终确认之前刷新了，从头再来；之后刷新了，只能用准备好的副本（第 3 节）调用 `settle`。
5. 不点释放、重置系统、更换镜像、保存镜像、升降配置、扩容、缩容、迁移、转包年包月、克隆、跨实例拷贝、修改SSH密码、充值、续费、发票，也不碰费用与账单里的任何操作。脚本的拒绝清单兜底，将要点的元素或对话框里有这些词时，它抛出 `refusal list: 词` 的错误，什么都不点。克隆是唯一的例外，只在用户开启了自动克隆时做，照 `reference/clone.md`，用的是 `reference/console-clone.min.js` 里另外的几个函数；平时贴的这一份里没有它们，这里的函数也点不了克隆。
6. 出现登录页（`page()` 返回的 `login` 为真）时，请用户本人在浏览器里登录，不代输入密码或验证码；登录后从第 2 节重来。
7. `rows()` 会读到同一账号下别的实例。别的实例的信息只在对话里用来核对，不写进任何文件，也不对它们做任何操作。

## 2. 每次用控制台之前

1. 用浏览器工具的 `navigate` 打开或刷新实例列表 `https://www.autodl.com/console/instance/list`。用哪个标签页都行，在后台、面板隐藏着也行；已有开着 AutoDL 的标签页就用它，里面可能还存着核对过的脚本。每次来用控制台、开始一串操作之前刷新一次（一串里上一个操作结算完了接着做下一个，不用再刷新），因为开得久的页面上数据可能是旧的（实测旧过约 2.5 小时），刷新也会清掉上次的脚本和残留的框。刷新后表格可能还在加载，`page()` 说找不到实例表时截一张小图再试；刷新后头几秒里开始操作的调用被拒绝、原因是按钮 `is covered by another element` 时也一样（实测遇到过一次，像是表格的加载遮罩还没撤），这时什么都没点，截一张小图再调用一次。
2. 设视口。内置浏览器的面板隐藏时，标签页的视口是 0×0，脚本会把所有按钮判为在视口外（拒绝原因里有 `is outside the viewport`）。用 `resize_window` 把这个标签页设成宽 1600、高 900。一轮对话结束或面板宽度变化时这个设置会被清掉，下一轮先再设一次；控制台的事做完后用 `resize_window` 的 `preset: desktop` 恢复。Claude in Chrome 下没有实测过，按钮不报在视口外就不用设。
3. 把页面脚本放进页面并核对。先用下面的短模板；它答 `stored: false`（这个标签页里还没贴过，或标签页重开过）时，改用完整模板。
4. 调用 `window.__autodl.page()`。返回 `list: true` 才继续；`login` 为真按第 1 节第 6 条；其余停下，说明不在实例列表，或页面结构变了。

完整模板。把 `reference/console.min.js` 的全文原样放在 `var fn =` 后面（约 34 KB，一个字符都不能改；不要贴带注释的 `console.js`，它的长度与校验和对不上），用浏览器工具的页面脚本功能在实例列表页里执行（内置浏览器是 `javascript_tool`）。刷新页面之后脚本就没了，要重新放一次，这时先用后面的短模板。

```js
(async function () {
var fn = /* 这里放 reference/console.min.js 的全文 */;
var t = fn.toString();
var b = new TextEncoder().encode(t);
var d = new Uint8Array(await crypto.subtle.digest('SHA-256', b));
var h = Array.prototype.map.call(d, function (x) { return ('0' + x.toString(16)).slice(-2); }).join('');
if (b.length !== 34095 || h !== '12350addfdfd6bd880179d9d8b51089c642ccc26d3fb590a22667dd866008f85') return { ok: false, bytes: b.length, sha256: h };
try { sessionStorage.setItem('__autodl_console_text', t); } catch (e) {}
var api = fn();
return { ok: true, version: api.version, mode: api.mode, page: api.page() };
})()
```

短模板。完整模板核对通过之后，把函数文本留在这个标签页的 sessionStorage 里（只有 `__autodl_console_text` 这一个键，关掉标签页就没了），为的是刷新之后不用再贴一遍。短模板把它取出来，照样核对长度与 SHA-256，一字不差才还原成函数执行，所以它在页面里被改过也会被认出来。脚本自己不读写任何存储，读写这一个键的是这两个模板。

```js
(async function () {
var t = null;
try { t = sessionStorage.getItem('__autodl_console_text'); } catch (e) {}
if (!t) return { ok: false, stored: false };
var b = new TextEncoder().encode(t);
var d = new Uint8Array(await crypto.subtle.digest('SHA-256', b));
var h = Array.prototype.map.call(d, function (x) { return ('0' + x.toString(16)).slice(-2); }).join('');
if (b.length !== 34095 || h !== '12350addfdfd6bd880179d9d8b51089c642ccc26d3fb590a22667dd866008f85') return { ok: false, stored: true, bytes: b.length, sha256: h };
var fn = (0, eval)('(' + t + ')');
var api = fn();
return { ok: true, version: api.version, mode: api.mode, page: api.page() };
})()
```

- 预期返回 `ok: true`、`version: 10`、`mode: 'live'`。脚本把自己挂在 `window.__autodl` 上，之后每次调用都写成 `window.__autodl.row('实例ID')` 这样的形式。
- 完整模板答 `ok: false`，说明贴进去的与文件不一样，脚本没有执行。从文件重新复制再贴一次；还不一样就停下，不要改文件或模板去凑。
- 短模板答 `stored: false`，是这个标签页里没有存着的文本；答 `ok: false` 而 `stored: true`，是存着的文本对不上。两种都改用完整模板贴一次（它会把存着的换掉）。短模板抛错（页面不让还原函数）时也一样，这种页面上以后每次都用完整模板。
- `mode` 为 `'none'`，或 `page()` 说页面里已有另一份脚本（another copy or version），就刷新页面，再按第 3 步放一次。

## 3. 调用与返回

- 每次用浏览器工具执行一个调用，例如 `window.__autodl.row('实例ID')`，读它的返回值。
- 返回值有四种。`{ok: true, ...}` 表示成功；`{ok: false, refused: '原因'}` 表示拒绝，这时什么都没点；`{ok: false, pending: true, why}` 表示还没准备好（框或选择器还在出现，或还在关闭），截一张小图再调用同一个函数；页面里抛出 `refusal list: 词` 的错误表示碰到了拒绝清单，什么都没点，按第 14 节停下。
- 截小图。面板隐藏时页面不出新帧，弹框和菜单停在动画起点，脚本会说它们还没完全显示。用浏览器工具截一张很小的图（内置浏览器是 `computer` 的 `screenshot`，`scale` 取 0.2 左右）就会出一帧。每次重试 pending 之前、每次 `settle` 之前都截一张。动画按时间走，一帧只推进到当时的进度，所以连着截几张没有用，每张之间隔一秒左右（实测隔一秒截两三张，框就显示完整了）。同一步 pending 重试 5 次仍不行，按那一步写的办法处理。截图自己偶尔会超时或报错（实测遇到过，浏览器工具说页面没来得及画完），这不算脚本的调用失败，什么都没点，再截一次或直接调用下一个函数。
- 准备好的副本。`bindDialog`（确认框）和 `prepareTimer` 返回 `copy`，最终确认成功时也再返回一份。最终确认之前就把它原样记在对话里，结算完才可以丢。页面刷新了，或最终确认的调用没有返回，就用它调用 `settle`。
- 调用本身失败时（浏览器工具报错、超时或没有结果，而不是返回了上面四种之一），不知道脚本有没有点。若是最终确认，按已尝试处理（第 9 节）；若是别的步骤，刷新页面从头来，做过预算检查的先按第 10 节 release。
- 省调用次数。浏览器工具能在一次调用里依次执行几个动作时（内置浏览器的 `browser_batch`），可以把几步排进一次，交替"等一秒、截小图、调用"。后一步要用前一步的返回值（`ctx`）时，在页面里放一个小函数，它只调用 `window.__autodl` 的函数、把返回值存进变量，不碰页面上别的任何东西，每调用一次前进一步，到了要等的状态之后只回一个状态。最终确认不排进去，单独放在预算检查与取 T0 之后的那一次调用里。每步之间留一秒，排得太紧时菜单与对话框还在动画里，会连着几次 pending（2026-10-03 实测）。

## 4. 读状态与有没有卡

`window.__autodl.row('实例ID')` 只读这一行，返回下面这些字段。

| 字段 | 内容 |
|---|---|
| `state` | 状态列的第一段文字，已关机、开机中、运行中或关机中 |
| `mode` | `'gpu'` 或 `'nogpu'`（状态列有"无卡模式"）；已关机时为 null |
| `gpuFree` | 状态列有"GPU充足"，即主机此刻有空闲 GPU |
| `gpuIdle` | 主机的"空闲/总量"，例如 `'1/8'`；读不出为 null |
| `timer` | 定时关机时刻 `'YYYY-MM-DD HH:MM:SS'`；没有为 null |
| `release` | 释放倒计时，例如"14天07小时39分后释放"；运行中是"关机15天后释放" |
| `spec`、`gpus` | 规格详情的文字（例如"RTX 3080 Ti * 1卡"）与其中的卡数；读不出为 null |
| `buttons` | 定时列与操作列的按钮文字，例如 `['设置定时关机', '开机', '更多']` |
| `place` | 这一行第一格里的地区与主机，例如 `'北京B区 / 123机'`，用户在控制台上凭它认这一行；读不出为 null |

- 状态是开机中或关机中时不点任何东西，隔一会儿刷新页面再读，等它变成运行中或已关机（脚本也只在已关机时开机、运行中时关机）。
- 有没有卡。已关机而且 `gpuFree` 为真，主机才有空闲 GPU；具体数量看 `gpuIdle`。数量几分钟内就会变，所以开有卡之前当场读（一两分钟之内读过、中间只设了定时的，不必为此再刷新；脚本在点"开机"与最终确认之前自己还会核对"GPU充足"）。没有卡就不开有卡，告诉用户（重试的间隔与次数见 SKILL.md 的出错处理）。"GPU充足"只在已关机的行上见过，`gpuIdle` 在运行中准不准没有实测过，不作依据：要知道有没有卡，关机之后再读。
- `rows()` 读所有行，`snapshot()` 读所有行的稳定部分（ID、状态、模式、定时、按钮），`dialog()` 读当前可见的框与选择器。
- 释放倒计时剩不到 3 天就提醒用户。
- 余额在控制台主页 `https://www.autodl.com/console/homepage/personal` 的"费用信息"里（"我的余额"的"可用"），用 `get_page_text` 读，只取这一个数。读余额要离开实例列表，页面脚本会跟着丢掉，所以放在第 2 节之前读；读完回到实例列表，从第 2 节做起。
- 欠费、余额不足与维护的提醒没有实测过，它们的位置与原文本手册给不出。读主页时（`get_page_text` 读到的全文，全站的横幅也在里面），页面上出现欠费、余额不足、停机、维护这类字样就按有提醒处理：不开机，把原文告诉用户。它与这台实例有没有关系不由你判断；用户看过之后在对话里说照开，才照开。主页上平时就有两处带着这类字样、却不是提醒，不算（2026-10-02 实测）："实例告警"一栏里的"余额不足预警 已开启 (余额不足10元预警)"是预警开关的名字；页面顶部的"上新通知"是产品公告。

## 5. 取消定时关机

前提是 `row` 的 `timer` 不为 null。凡是要去掉这一行的定时都照这一节做，实例关着、开着都可以：开机之前这一行有定时、而这次开机不需要（SKILL.md 开机流程第 2 步，不管它是谁设的）；设了定时而这次没开成，取消自己设的；确认开机之后多出来的（开机流程第 6 步）；arm 成功之后取消开机前设的临时定时（开机流程第 8 步）；关机之后这一行还挂着的（SKILL.md "关机"里关掉之后的第 1 步）。取消的不是你设的，在汇报里提一句。已过点的定时在关着的实例上照样显示（带"修改""关闭"），`timer` 不为 null，同样照这一节取消（2026-10-03 实测）。

1. `startCancelTimer('实例ID')`，返回 `{ok: true, ctx}`，脚本点了定时时刻旁的"关闭"。记下 `ctx`。
2. 截小图，`bindDialog(ctx)`，预期 `kind: 'box'`、`text: '取消定时关机'`，带 `copy`，记下。
3. `confirm(ctx)`，返回 `stage: 'attempted'`，这是最终确认。返回 refused 时脚本没有点，`dismiss(ctx)`（它也被拒绝就刷新页面），再从第 2 节重来一次；调用没有返回时按已尝试处理，用 `copy` 走第 9 节。
4. 按第 9 节结算，预期 `confirmed`；之后这一行的 `timer` 为 null，按钮回到"设置定时关机"。

## 6. 有卡开机

前提是用户的模式用法里有有卡；`row` 显示已关机、`gpuFree` 为真、`gpus` 至少为 1；这一行的定时关机已经照开机流程第 2 步弄好（这次开机该有的已经设上，不该有的已经取消）。

1. `startPowerOnGpu('实例ID')`，脚本点了"开机"。没有"GPU充足"或读不出卡数时它拒绝，什么都不点。
2. 截小图，`bindDialog(ctx)`。预期 `text` 是"确认开机吗？ 实例将按￥0.98/时整点扣费"这样的原文（单价随实例），返回 `price`（元/时）、`gpus`（打开操作时读出的卡数）、`spec` 与 `copy`。记下 `copy`。
   - 先比余额。按这个单价，第 4 节读到的余额不够付计划时长的，`dismiss(ctx)`，不开机，告诉用户，由用户决定；这时还没做预算检查，没有预留。用户说照开，就从第 1 步重来，这次不再比。
3. 预算检查，`ctl auth check --instance <实例ID> --mode gpu --price <price> --gpus <gpus> --hours <计划时长>`，单价与卡数都用第 2 步返回的值。`--hours` 写十进制小时，例如 `2` 或 `1.5`，最多三位小数，不能写 2h 或 90m；除不尽就向上取（8 分钟写 `0.134`）。
   - 退出 0 时，输出里的 `req` 是这次的请求号，记下，进第 4 步。
   - 退出 10、11、12 时，`dismiss(ctx)` 点"取消"，按输出告诉用户（预算不够或要先问用户、本机记录不能用、没有授权或授权里没有这种模式）。这时没有预留，不用 release。
   - 退出 1、输出说本周期的扣费还没导入时，`dismiss(ctx)`，照第 12 节读收支明细并导入（一笔都没有就导入 `'[]'`），再从第 2 节重来。这时也没有预留。
   - 其他退出码，`dismiss(ctx)`，停下报告。
   - 这几种里不再接着开的，开机前自己设的定时关机按第 5 节取消，不留给下一次开机。
   - 调用没有结果（不知道退出码）时，预留可能已经记上了，也可能没有，还可能稍后才记上。`dismiss(ctx)`，不开机，也不重跑；用 `ctl auth show --instance <实例ID>` 列出 `open_reservations` 告诉用户，由用户决定哪些 release。不要自己推断哪一个是这次的，别的对话可能刚好也建了预留。
4. `ctl now`，输出的数字就是 T0（unix 秒），原样记下。
5. 立刻 `confirm(ctx)`。返回 `stage: 'attempted'` 就是最终确认已做。
   - 返回 refused 时脚本没有点。`dismiss(ctx)`（它也被拒绝就刷新页面），再 `ctl auth release --instance <实例ID> --req <req>`，同一个上下文不再调用 `confirm`。看拒绝原因，"GPU充足"没了就按没有卡处理；卡数或规格变了、某一行变了、行节点换了，刷新页面从第 2 节重来一次（重新做预算检查）；其余停下报告。
   - 调用没有返回时，按已尝试处理，用 `copy` 走第 9 节。
6. 按第 9 节结算。`confirmed` 之后立刻 `ctl log on --instance <实例ID> --req <req> --at <T0> --field mode=gpu --field price=<price> --field gpus=<gpus>`（结果怎么看在第 10 节），不等后面的步骤，它们哪一步失败这次开机都已在账上。再读一次 `row`，`timer` 应是开机前留下的样子（设了的是那个时刻，没设的是 null）；不是，就照开机流程第 6 步弄对。然后按 SKILL.md 的开机流程往下做（等实例起来、核对主机名、部署与 arm；开机前设的是临时定时的，arm 成功后按第 5 节取消）。

## 7. 无卡开机

前提是用户的模式用法里有无卡；`row` 显示已关机；这一行的定时关机已经照开机流程第 2 步弄好。官方说明同一账号同时只能有一台实例在无卡模式，但实测有过另一台显示无卡模式时照样开成的情况，所以不因为看到别的行是无卡模式就不开；平台真的报冲突时，按第 9 节与 SKILL.md 的出错处理办。

1. `menu('实例ID')`。第一次通常返回 `open: false`（脚本刚派发了悬停）；截小图，再调用一次，预期 `open: true`，`items` 的第一项是"无卡模式开机"。还是 `open: false` 就再截小图、再调用（展开的动画要出几帧才走完，实测要两三次），5 次仍不开就停下。第一项不是"无卡模式开机"也停下；其余各项这里用不到，平时是哪些记在第 15 节，只作备查。
2. `startPowerOnNoGpu('实例ID')`，脚本点了"无卡模式开机"。
3. 截小图，`bindDialog(ctx)`（返回 pending 就截小图再试，实测要两三次）。预期 `text` 是"确认无卡模式开机吗？ 无卡模式配置为:0.5核心CPU，2GB内存，无GPU卡 配置费用:￥0.10/时，最低消费￥0.01"（返回的原文里各句之间可能没有空格），返回 `price` 与 `copy`，记下。
   - 先比余额，同第 6 节第 2 步。
4. `ctl auth check --instance <实例ID> --mode nogpu --price <price> --gpus 0 --hours <计划时长>`，退出码的处理同第 6 节第 3 步。
5. `ctl now` 记下 T0，立刻 `confirm(ctx)`；refused 与没有返回的处理同第 6 节第 5 步。
6. 按第 9 节结算。`confirmed` 之后同第 6 节第 6 步，`log on` 用 `--field mode=nogpu --field price=<price> --field gpus=0`。

展开菜单后决定不开了，调用 `leaveMenu('实例ID')` 让菜单收起。

## 8. 设置或修改定时关机

定时关机由平台到点直接关机，会切断正在跑的任务。实例关着时也能设，带着定时照样能开机。三种时候用这一节。

- 用户选了控制台定时关机。在开机之前设（开机流程第 2 步），点确定的那一刻硬上限就已经在了；接手一台开着的实例、这一行没有而用户选了的，也照这里设
- 开机前的临时定时。用户没选，而 `ctl auth show` 的 `guard_at_boot` 里没有要开的模式（守护不会在容器启动时自己起来，典型的是第一次在这台实例上用）：设到 30 分钟之后，arm 成功后按第 5 节取消。它只管点确定到 arm 之间的那一两分钟，对话要是在这当中断了，到点平台会关机
- 只读服务器时间，核对本机时钟时用：做到第 3 步为止，然后 `dismiss(ctx)`

1. `startSetTimer('实例ID')`，脚本点了"设置定时关机"（已有定时时点"修改"）。
2. 截小图，`bindDialog(ctx)`，预期 `kind: 'dialog'`、`text: '定时关机'`。
3. `readTimer(ctx)`，读出 `serverTime`，即对话框里的当前服务器时间，形如 `2026-10-01 12:05`，不带秒。定时时刻按它算，只到分钟，注意跨日。临时定时不论什么时候设，都是服务器时间加 30 分钟。用户选的定时，开机之前设的是服务器时间加上用户选的时长；开机之后才设的（接手，或开机前没设上、这时补设），是服务器时间加上这次开机剩下的时长：用户选的时长减去从 T0 到现在过去的时间，过去的时间用 `ctl now` 的输出减 T0；接手的开机没有 T0，用 `ctl status` 的 `booted_at`，见第 17 节。开机之前设的定时是从设的那一刻算的，到真正点下开机还要一两分钟，所以它比"开机后这么久"早到点一两分钟；用户选的时长只有十来分钟时这段差别不小，启动任务前按定时的时刻算，不按用户说的时长算。服务器时间是北京时间（2026-10-02 同本机时钟对过，到分钟一致）。拿它核对本机时钟时，把 `ctl now` 换成北京时间再比；两者相差接近整小时的倍数时可能只是时区的差别，不据此说本机时钟不对，请用户确认。用命令算，不心算，例如 `python -c "import datetime as d; s = d.datetime.fromisoformat('<serverTime>'); print((s + d.timedelta(seconds=<要加的秒数>)).strftime('%Y-%m-%d %H:%M'))"`（`python` 换成 `ctl doctor` 报出的那个 Python）。
4. `openTimerPicker(ctx)`，截小图，`bindTimerPicker(ctx)`（pending 就截小图再试）。
5. `focusTimerInput(ctx, 'date')`，然后用浏览器工具全选（`computer` 的 `key` 发 ctrl+a，Mac 上 cmd+a），输入日期 `YYYY-MM-DD`，按回车。
6. `focusTimerInput(ctx, 'time')`，同样全选，输入 `HH:MM`，按回车。
7. `readTimer(ctx)`，`date` 与 `time` 应是刚输入的值。不是就再做一遍第 5、6 步；还不对，`dismiss(ctx)`，停下报告。选择器在回车后自己关了（`readTimer` 说 bound picker is gone）时，`dismiss(ctx)`，刷新页面重来，这次时间输入后不按回车。
8. `confirmTimerPicker(ctx)`，脚本点了选择器底部的"确定"。截小图。
9. `prepareTimer(ctx)`（pending 就截小图再试），返回 `expect`、`cost`（预计消费）与 `copy`，记下 `copy`。对话框的日期框只显示到分钟（例如 `2026-10-02 02:16`），`expect` 是脚本补上秒之后的时刻（`2026-10-02 02:16:00`），设成之后这一行显示的就是它。`expect` 必须等于第 3 步算出的时刻加上 `:00`，不等就 `dismiss(ctx)`，刷新页面从头来。`cost` 应大致等于单价乘以时长（实例关着时按有卡单价算，开无卡之前设的也一样），差得离谱就 `dismiss(ctx)`，停下报告。开机之前设时确认框还没打开，有卡单价取这台实例上一次有卡开机的（项目的开关机记录里有）；从没见过它的有卡单价时，这一项不核对，只核对 `expect`。
10. `confirmTimerDialog(ctx)`，这是最终确认，脚本点了对话框底部的"确定"。返回 refused 时脚本没有点，`dismiss(ctx)`（它也被拒绝就刷新页面），再从第 2 节重来一次；调用没有返回时按已尝试处理，用 `copy` 走第 9 节。
11. 按第 9 节结算，预期 `confirmed`，这一行的 `timer` 等于 `expect`；`prompts` 里通常有"设置成功"。

面板隐藏时浏览器工具照样能把字输进选择器（2026-10-02 在内置浏览器里实测；输完日期按回车，日期框先填上日期与当时的钟点，输完时间再变成所选的时刻）。第 7 步读不到输入的值时，`dismiss(ctx)`，告诉用户，请用户把浏览器面板打开再试，或由用户决定不设控制台定时关机。临时定时也一样：设不上（这里打不进字，或前面哪一步被页面脚本拒绝）就不自己开机，告诉用户这次开机到 arm 之间的一两分钟没有兜底，由用户决定开不开。

开机前设了定时、而这次开机后来没开成（预算检查没过、没有卡、用户改了主意）：把自己设的定时按第 5 节取消，不留给下一次开机，那可能是用户手动开的。

开机前设的定时是按设的那一刻算的。设完之后隔了十分钟以上才要点确定的（中间等过用户，或重试过），先照这一节把它改到新的时刻再开：临时定时可能已经快到点，而在关机期间过了点的定时，开机之后会怎样没有实测过。

## 9. 最终确认之后的结算与查明

1. 每隔约 5 秒截一张小图，调用 `settle(ctx)`（页面刷新过或最终确认没有返回时用 `settle(copy)`），最多等 60 秒。
2. 返回的 `result` 有三种。
   - `confirmed`，目标行按预期变了，别的行没变，没有错误提示，也没有任何框。操作结束。
   - `pending`，还没变，或已按预期变了而框还在关。继续等，到 60 秒仍是 pending 就按 uncertain 处理。
   - `uncertain`，其余情况。`prompts` 是页面上可见的提示与框的原文；`changed.target` 说目标行没变（`unchanged`）、按预期变了（`as expected`）还是变得不对（`unexpected`）；`changed.others` 说别的行有没有变。
3. uncertain 时按下面查明，期间不点任何东西。
   - 提示原文明确说没成功（例如 GPU 不足、余额不足、已有实例在无卡模式），`changed.target` 是 `unchanged`，而且刷新页面后读 `row` 仍是原样，才算没开（或没设上）。开机的话这时按第 10 节 release，再按 SKILL.md 的出错处理办。这是开机不做下一条三项核对就 release 的唯一情形。
   - 开机。刷新页面、放好脚本（第 2 节）、读 `row`。开机中或运行中、模式对，就是开了，按开机流程往下做，用原请求号 `log on`。仍是已关机，隔一分钟再刷新读一次，再用 `ctl wait <别名> --mode <模式> --timeout 2m` 看连不连得上，并看收支明细（第 12 节）里 T0 之后有没有这台实例的扣费；三样都说没开才算没开，按第 10 节 release；之后把这次的异常告诉用户，可以从开机流程第 1 步重新开始一次（预算检查重做）。状态是别的样子或说不清，告诉用户，预留先保留。
   - 定时。刷新后读 `row` 的 `timer`，等于 `expect` 就是设上了；还是原来的，就是没设上，可以重新开始一次设置。
   - 取消定时。刷新后读 `timer`，为 null 就是取消了，否则可以重新开始一次取消。
   - 别的行变了（`changed.others` 为真）时，先按上面查明目标行，再把变化告诉用户；别的实例一概不碰。

## 10. 预算的预留

| 情形 | 怎么办 |
|---|---|
| `auth check` 退出码不是 0 | 没有预留 |
| 检查通过后放弃（`dismiss`、最终确认前刷新了页面、`confirm` 被拒绝） | 立即 `ctl auth release --instance <实例ID> --req <req>` |
| 结算为 `confirmed` | 立刻 `ctl log on --instance <实例ID> --req <req> --at <T0> --field mode=... --field price=... --field gpus=...`，不等开机流程后面的步骤 |
| uncertain，提示明确说没开、目标行没变，刷新后 `row` 仍是原样 | release（唯一不做第 9 节三项核对的情形） |
| 其余 uncertain、pending 超时、最终确认没有返回 | 先保留；查明开了，用原请求号 `log on`；查明没开，release |
| `auth check` 的调用没有结果 | 不开机；用 `ctl auth show` 列出未落定的预留告诉用户，由用户决定，不自己猜着 release |

- 预留不会自己消失。它一直算在预算里，直到被 `log on` 用掉或被 release；`auth check` 输出里的 `expires` 只表示它覆盖的时间窗到哪里。所以每个预留最后都要落到 `log on` 或 release。
- release 可以重复执行；已经被 `log on` 用掉的预留不能再 release。

`log on` 的结果要看清。

- 退出 0、`ledger` 为 `recorded` 或 `resend`、`session` 等于请求号，才算记好。
- 调用没有结果时，用同一个 T0 和同样的字段重发，重发得到 `resend`。
- 退出 1、`ledger` 为 `mismatch`（`session` 是 m 加请求号）时，账本已按这次给的值另记了这次开机，原预留仍占预算。核对模式、单价与卡数确实是这次开机的实际值后 release 原请求号，并告诉用户。核对发现是自己传错了值（记下的不是实际值）时，账本里这条记录改不了；不要自己 release，把记错的值与原预留都告诉用户，由用户决定。
- 退出 1、说这台实例还有一段开着的会话时，看拒绝里写的那段会话的开始时刻（`on since`）。
  - 早于你的 T0，是上一次开机没记关机（它本该在开机流程第 1 步就补上，走到这里是那时没补成）。按第 12 节从收支明细读出 T0 之前这台实例最后一笔扣费的时刻，先 `log off`，再用同一个 T0 重发 `log on`。收支明细读不到时，等实例起来后取 `ctl status` 的 `last_shutdown_at` 作关机时刻（它晚于那次开机才算数），`log off` 时加 `--field time=estimated`；它也不比那次开机晚时（那次是在控制台关的、定时关的，或用 `off-raw` 关的），请用户看一眼自己的收支明细，把那笔扣费的时刻告诉你。这种情况下开机前的预算检查把旧会话一直算到现在，只会多算，因此退出 10 时把原因告诉用户。
  - 不早于你的 T0，是这次开机已经被接手它的另一个对话记上了（拒绝里也这样写）。不补 `log off`。看一眼那段会话的模式、单价与卡数（`ctl auth show` 的 `open_session`），然后同 `mismatch` 一样 release 你自己的请求号，并告诉用户。记下的值与确认框里的不同（多半是接手的对话估的单价）也照样 release，把记下的值告诉用户；账本里这条记录改不了，钱以导入的扣费为准。
  - 接手一台已经开着的实例不走这一条，做法在第 17 节。
- `log off` 退出 1、说关机时刻早于开机时，先核对自己这一边：取的是不是这台实例的行里最晚的一笔，北京时间换算得对不对，再读一遍收支明细看关机那一笔是不是刚出来。都没错，最后一笔扣费确实比开着的那段会话的开始（`ctl auth show` 的 `open_session`）还早，就不要换一笔扣费去凑。这是那段会话的开始时刻记得不对：会话很短而本机时钟比平台快，平台没开成也没扣费，或开始时刻是本机时钟超前时写的。告诉用户，用户同意后 `ctl log off --instance <实例ID> --void --quote '<用户原话>'`，它按会话自己的开始时刻关掉这一段，再照第 12 节导入扣费，钱以扣费为准。这一段的用量此后不在账上：实例其实还开着，或预算按 GPU 小时算时，照 `reference/ledger.md` 里 `--void` 一条把真实的用量补回去。
- 退出 11 时账本没记上（本机记录不能用）。再看 `project_log`，写了就只差账本，没写就两处都要修。实例照常往下用（arm、关机都照常；本机记录修好之前，带别名的命令要加 `--instance <实例ID>` 才肯做，见 `reference/ledger.md` 的"本机记录"），告诉用户；修好后用同一个 T0 和字段重发。修好时已经关过机的，按先后补，先重发 `log on`，再用原来的时刻重发 `log off`，最后导入扣费。
- 退出 1、`project_log` 说没写上时，账本已经记好，排除项目日志的问题后重发。
- 已经开了机，就不要把原预留当成没用过去 release。只有两种情形例外，`mismatch`，与上面"开着的会话不早于你的 T0"：这两种里开机都已经另记在账上，原预留不放掉就算了两份。
- `log on` 在确认之后立刻做，模式、单价与卡数就是预算检查用的那三个值。之后才发现实际开成了别的模式（要有卡却成了无卡）时，账本里这次仍按原来的模式算，只会多算；照 SKILL.md 的出错处理关机，关机后导入扣费，并告诉用户。
- `auth release`、`log off` 与 `auth charges` 也只有退出 0 才算做成。退出 11 时账本里没有记上（`log off` 照样写了项目日志），本机记录修好后原样重发：同一个请求号，同一个 `--at`，同样的扣费行。

## 11. 刷新页面前后

- 最终确认之前刷新（或页面自己跳走），脚本和操作都没了，什么也没确认。做过预算检查的先 release，然后从第 2 节重来。
- 最终确认之后刷新，按第 2 节重新放好脚本，只用 `settle(copy)` 结算，按第 9 节查明；查明之前不为同一个目的开始新的操作。
- 刷新会清掉页面上残留的框；脚本从不碰它没绑定的框。
- 开机、设置或取消定时确认之后，页面会自己在地址后面加上 `?_random_=...`（实测）。这不是刷新，脚本和进行中的操作都还在，照常 `settle`。

## 12. 读扣费

- 收支明细在 `https://www.autodl.com/console/cost/incomeExpend`（左侧菜单"费用"展开后的"收支明细"），只读，用 `get_page_text`（`max_chars` 给够，一页 100 行约一万多字；`find` 最多只回 20 条，行多时会漏）。
- 它每页默认只有 10 行，账号下所有实例的行混在一起、按时间倒排，表格下面的"共 N 条"是总行数。别的实例也在扣费时，要找的行很快就不在第一页了。翻页不点页面上的任何东西，直接用 `navigate` 打开带参数的地址 `https://www.autodl.com/console/cost/incomeExpend?page_size=100&page_index=<页码>`（2026-10-02 实测，每页 100 行可用），从第 1 页读起，读到要找的那一笔，或读到比要找的范围更早的行为止。翻了 10 页还没到头，就不再往下读，把读到哪一天告诉用户，由用户决定。
- 列依次为流水号、交易时间、收支类型、交易类型、交易渠道、交易金额、账户余额、备注。只取备注为"容器实例ID：<实例ID>"的行（另有带"数据盘"的一种，见下面），别的实例的行不用、不记。
- 按量计费的实例运行中每到 XX:59:59 结一笔，关机时再结一笔，所以一次开机最后一笔扣费的交易时间就是关机时刻。一次开机最少收 ￥0.01。
- 数据盘有付费扩容的实例，另有一种行，备注是"容器实例ID：<实例ID> 数据盘"，比上面的多"数据盘"三个字。它是扩容的日常费用，每天 23:59:59 扣一笔，实例关着也扣（2026-10-03 实测）。它不是开机的扣费，取关机时刻时不算它；它是这台实例的花费，导入账本时同别的行一样带上，并在这种行里写 `"disk": true`（只收 23:59:59 的行，别的时刻标了整批拒绝）。实例开着时 23:59:59 也有一笔开机的扣费，这一秒常常两种行都有，按备注分。登记过日常费用的实例（`ctl auth show` 的 `daily_fen` 不为 0），23:59:59 的开机扣费行要写 `"disk": false`，这一秒的行哪一种都不写明，整批拒绝。
- 关机后 `ctl log off --instance <实例ID> --at <那一笔的 unix 时间>`。交易时间是北京时间，用命令换成 unix 时间、在同一条命令里传给 ctl，不手抄（Bash 工具每次调用不保留变量），例如 `AT=$(python -c "import datetime as d; print(int(d.datetime.fromisoformat('2026-10-01 11:45:26+08:00').timestamp()))") && ctl log off --instance <实例ID> --at "$AT"`（`python` 换成 `ctl doctor` 报出的那个 Python）。
- 把扣费行导入账本，`ctl auth charges --instance <实例ID> --json '[{"serial": "<流水号>", "instance": "<实例ID>", "time": "<交易时间>", "amount": "<金额>"}]'`。金额写正数、不带￥（例如 `"0.14"`），一次可以给多行，数据盘的行另加 `"disk": true`（见上面说数据盘的那一条）。流水号与交易时间从页面文本原样复制，不凭记忆重打。导入之后看输出：`already` 是以前导入过的行数，`imported` 是这次新记进去的，通常等于这次开机的行数。`imported` 比这多时，先看多出来的是不是以前没导入过的行（没人记账的开机，或上一次收尾没导入）；都不是，就是有一行的流水号抄错、被当成新的一笔又算了一次（预算只会多算），告诉用户。页面上这台实例本周期的扣费行都带上，不只这次开机的：导入过的行会被认出、不重复，而没人记账的开机（用户手动开的、两次对话之间的）这样也进了金额预算。本周期指授权的那个周期：按月的预算是这个月；不分周期的预算从授权那一刻算起，只带授权之后的行。
- 按月的金额预算，每次 `ctl auth grant` 之后、以及每个月的头一次预算检查之前，也要读一次、导入一次，不导入 `auth check` 不放行（不分周期的预算与 GPU 小时预算不用，grant 输出的 `note` 写着各自从哪里算起）。这台实例本周期一笔扣费都没有，就导入空列表，`ctl auth charges --instance <实例ID> --json '[]'`，意思是读过、没有。用户说这个周期开过机而明细里一行都没有，对不上：告诉用户，等用户看过自己的收支明细再导入，不猜。按月的预算要把这个月的行读全（翻页的办法见上一条）；没读全就导入的，把缺的是哪一段告诉用户，预算在那一段上是少算的。
- 收支明细读不到（页面打不开，或结构与这里写的对不上）时不猜，请用户看一眼自己的收支明细再告诉你。开机流程第 1 步要补一次没记上的关机、而这时读不到又等不到用户：照常往下开机，预算检查只会多算；开机后照第 10 节"早于你的 T0"一条补。
- 余额与流水号只用于这次核算，不写进项目文件，不外传。项目 `## AutoDL` 段的 gpu_used 只记累计的用量与累计的费用，取 `ctl usage` 的数（读本项目的开关机记录，费用按单价估）；`ctl usage --instance` 是这台实例在所有项目里的合计，不当作本项目的。

## 14. 对不上就停下

以下情况停下，把函数返回的原因或原文告诉用户，不猜、不绕过。

- 确认框或对话框的原文与本手册不符（`the dialog text does not match`、`the dialog title does not match`），或菜单项不符。拒绝原因里带着框里的原文。这时框没有绑定，`dismiss(ctx)` 会被拒绝，刷新页面把它关掉；绑定在预算检查之前，所以没有预留要处理。
- 抛出 `refusal list: 词`。若来自 `bindDialog`，对话框还开着，先 `dismiss(ctx)`；不行就刷新页面。
- 同时有两个框（`more than one dialog`），或出现本手册没写的提示。
- `page()` 说不在实例列表或页面结构变了，或者各行的实例 ID 不唯一。
- 同一个拒绝原因按本手册处理后仍在。

停下之前若已做过预算检查、还没最终确认，按第 10 节 release。停下之后用户仍要开机的，由用户本人在控制台点，照第 16 节做：预算检查、T0 与记账还是你来，按钮由用户点。
