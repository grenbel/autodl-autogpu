# AutoDL 控制台操作手册：少用的四节

`reference/console.md` 的续篇，节号接着它排。平时开机、关机用不到这里的内容，遇到对应的情形再读；要用页面脚本时，`reference/console.md` 第 1 到 3 节的规则在这里同样适用。

## 13. 控制台关机

只在两种情况下用，开机后 SSH 始终连不上（不能用 `ctl off-raw`），或用户当场同意。SSH 连不上时先照 `reference/ssh.md` 的"别名的写法与第一次连接"查原因：别名写错了，或这台实例的主机密钥还没被接受，都是修得好的，修好就不用在控制台关机。

这一版的脚本对关机确认框只读不点，`confirm` 对关机一律拒绝。它的原文 2026-10-02 读到过一次，是"确认关机吗？实例：<实例ID>"（一句问话加一行"实例："与这台实例的 ID，按钮是"取消""确定"）；放行要等这段原文写进脚本并经过审查。现在这样做。

1. `startPowerOff('实例ID')`（只在运行中可用），截小图，`bindDialog(ctx)`，读出 `text`，返回里有 `reviewed: false`。原文与上面写的不同，或"实例："后面不是这台实例的 ID，照样 `dismiss`，并把原文告诉用户。
2. `dismiss(ctx)`。
3. 把原文告诉用户，请用户本人在控制台点"关机"，并告诉你点的时刻；之后按第 12 节读扣费、`log off`。

## 15. 原文与结构备查

- 实例列表的列依次是实例ID/名称（区与机器号在上，ID 在下）、状态、规格详情、本地磁盘、健康状态、付费方式、释放时间/停机时间、SSH登录、快捷工具、操作。表格没有固定列，视口不够宽时右边几列在视口外。
- 已关机的行，状态是"已关机"，主机有空闲卡时跟着"GPU充足"；释放列是"N天N小时N分后释放"（从关机时起算 15 天）与"设置定时关机"；操作列是"开机""更多"。运行中的行，状态是"运行中"，无卡时跟着"无卡模式"；释放列是"关机15天后释放"；操作列是"关机""更多"。有定时关机时，释放列是"YYYY-MM-DD HH:MM:SS"与"修改""关闭"。
- "更多"菜单依次是无卡模式开机、更换镜像、保存镜像、升降配置、扩容数据盘、缩容数据盘、转包年包月、克隆实例（后面带一个"新"字）、跨实例拷贝数据、修改SSH密码、重置系统、释放实例。本手册只用第一项。
- 确认框（`el-message-box`）的原文。有卡开机是"确认开机吗？ 实例将按￥X/时整点扣费"；无卡开机是"确认无卡模式开机吗？ 无卡模式配置为:0.5核心CPU，2GB内存，无GPU卡 配置费用:￥0.10/时，最低消费￥0.01"；取消定时是"取消定时关机"。按钮都是"取消""确定"。框里不写是哪台实例，所以脚本靠绑定的节点和各行的快照保证没有点错行。
- 定时关机对话框（`el-dialog`）的标题是"定时关机"，内容依次是当前服务器时间（不带秒，后面跟一句"如和您本地时间有差异，以下定时关机时间请以服务器时间为准"）、定时关机时间（日期框，选好后只显示到分钟）、预计消费（没选时间时显示"选择时间后计算费用"，选好后是一个金额）、账户余额、账户代金券，底部是"取消""确定"。时间选择器有"选择日期""选择时间"两个输入框，底部是"此刻""确定"。两个"确定"由脚本按所属容器区分。
- 定时精确到分钟，提交后弹出"设置成功"。运行中与关机时都能设，关机时预计消费按有卡单价算。实例提前关机后定时仍然挂着，还没到点的旧定时在下次开机后照样生效、到点关机。所以关机收尾时把还挂着的定时取消（第 5 节）；开机之前也不让旧定时照原样留着，这次开机不需要定时就取消，需要就改成这次的时刻（第 8 节）。这两步都要有一个对话在场才做得了，有三种时候做不了，定时会留在这一行上：开机前设好了定时、还没点开机对话就断了；arm 之后、取消临时定时之前对话断了；对话已经结束，守护自己按空闲关了机，而用户选的定时还没到点。所以要告诉用户，自己在控制台手动开机之前先看这一行的定时关机，有就取消或改掉。
- 开机很快，点确定后约 10 到 21 秒 SSH 就能登录；关机后约 5 到 26 秒停止计费，看关机的方式。
- 容器的主机名是 `autodl-container-<实例ID>`，开机后据此核对 SSH 别名连的是这一台。控制台里的 SSH 登录指令与密码是打码的，不要点显示它们的按钮。

## 16. 没有浏览器工具时

没有能在页面里执行脚本的浏览器工具时（怎么算没有，见 SKILL.md 的"没有浏览器工具时"），开机不能自动做，要明确告诉用户这台电脑上开机要用户自己点。

1. 说清点哪一行的哪个按钮、开哪种模式。开机前本来由你读的几样也请用户看一眼，有没有欠费、余额不足或维护的提醒，余额（控制台主页"我的余额"的"可用"）是多少，这一行有没有"GPU充足"（开有卡时），有没有定时关机，释放倒计时还剩多久。定时关机照开机流程第 2 步的三种情形请用户弄好：用户选了的请用户这时就设；不需要的，有就请用户点"关闭"取消；守护还不会自己起来、用户又没选的，请用户先设一个半小时后的临时定时，arm 成功后再请用户取消。用户不愿设，就说明这次开机在你 arm 之前没有兜底，对话要是在这一两分钟里断了请在控制台关机，然后照开。然后请用户点到确认框为止，先不要点确定，把框里的单价和这一行规格详情里的卡数告诉你。
2. 按用户报的单价，余额不够付计划时长的，请用户点"取消"，由用户决定（用户说照开，就请用户重新点到确认框，这次不再比）。够付就 `ctl auth check`（同第 6 节第 3 步，无卡时 `--gpus 0`）。退出 0 就记下 `req`，否则请用户点"取消"，按输出告诉用户。
3. `ctl now` 得到 T0，再请用户点确定。不要用用户说的钟点代替 T0。
4. `ctl wait <别名> --mode <模式>` 等实例起来。起来了先用原请求号和这个 T0 `log on`，再按开机流程往下做。用户明确说没点确定、或者点的是取消，就 release。点过确定却没起来，或者说不清，按第 9 节的办法查明，只是行的状态与收支明细都请用户读给你，SSH 用 `ctl wait` 看；全部说明没开才 release，查不清就保留预留并告诉用户。
5. 定时关机设到什么时刻由你算好告诉用户（第 8 节第 3 步的算法，服务器时间请用户从定时对话框里读给你），由用户在控制台里设；arm 成功之后，临时设的那一个请用户取消。
6. 关机本身照常由你用 ctl 做。收尾里要看控制台的三样请用户代看：这一行的状态是不是"已关机"；这一行还挂着定时关机就请用户点"关闭"取消；收支明细里这台实例最后一笔扣费的时刻与金额（连同要导入的扣费行）请用户读给你。用户一时不在，先用 `ctl wait <别名> --state down` 的结果，等用户回来再补 `log off` 与导入。

## 17. 接手已经开着的实例

次序在 SKILL.md 的"接手已经开着的实例"，这里是每一步的细节。接手没有 T0，凡是要用 T0 的地方都用 `ctl status` 的 `booted_at`（这次开机容器启动的时刻，按本机的时钟）。`booted_at` 只属于给出它的那次 status：中间等过用户或隔了一阵，先再跑一次 `ctl status`，实例可能已经关过又开了。

**记账。** `ctl auth show --instance <实例ID> --booted-at <booted_at>`，`this_boot` 有三种回答。

- `recorded`，开着的会话开始得不早于这次启动之前 120 秒，算这次开机的，不再记。先把 `open_session` 的模式与卡数同 `row` 的 `mode`、`gpus` 比一下（无卡时卡数是 0），一致才算数，单价就用 `open_session` 的。不一致，它多半不是这次开机（一次没记关机的开机之后两分钟内又开了一次），按下面"更早的一段"查收支明细；查不到那笔关机扣费，就是这段会话记的模式或卡数不对，告诉用户，由用户决定（`ctl log on --booted-at` 带着实际的模式与卡数时，ctl 自己也会拒绝并说明这两种可能）。
- `not recorded`，没有开着的会话。`ctl log on --instance <实例ID> --booted-at <booted_at> --field mode=<模式> --field price=<单价> --field gpus=<卡数>`，会话从这次启动的时刻算起。卡数用 `row` 的 `gpus`。单价先看收支明细（第 12 节）：这次开机已经跨过两个整点时，第二笔整点扣费盖满一小时，它的金额就是单价；没有就问用户（开机确认框里的那个数）；用户说不上来才用项目开关机记录里同一种模式上一次的单价，并在汇报里注明是估计。
  - 这时 `open_reservations` 里有不是你建的预留，多半是另一个对话正在开这台机器、还没走到 `log on`（开机流程第 1 步说的"等用户答复再往下做"，是实例关着、准备开机时的做法；实例已经开着时照这里办）。隔一分钟再看一次。仍然如此，告诉用户，照上面记这次开机，并在用户同意后 `ctl auth release --instance <实例ID> --req <那个请求号>`：开机已经另记了，那条预留不放掉就算了两份。只有 release 要等用户的答复，记账、预算与后面的 deploy、arm 照常做。
- `an earlier session is still open`，开着的会话比这次启动早 120 秒以上（更早的一段）。两次开机之间一定隔着一笔关机扣费，所以看收支明细里这台实例在 `open_session` 的开始时刻（`on`）之后、`booted_at` 之前有没有扣费。
  - 有，那段会话是更早的一次开机、关机没记上。用其中最后一笔的时刻补 `ctl log off --instance <实例ID> --at <那一笔的 unix 时间>`，导入扣费，再照 `not recorded` 记这次（gpu_used 等这次关机收尾时一并更新）。不要用这次开机自己的整点扣费去关它。
  - 没有，说明从那段会话开始到现在没关过机，它就是这次开机的（T0 记得早，或容器起得慢），什么都不记。同 `recorded` 一样先比一下模式与卡数，一致后模式、卡数与单价就用 `open_session` 的。
  - 收支明细读不到时，请用户看一眼自己的收支明细再告诉你，不猜。
- `booted_at` 为 null（算不出）时不猜。请用户说这次大约是什么时候开的，换成 unix 时间作 `--booted-at`，`log on` 时加 `--field time=estimated`。

不给还开着的会话补关机。`log on --booted-at` 回答 `already` 是这次开机已在账上，也算记好。`recorded` 或查明是这次开机之后，`open_reservations` 里还有不是你建的预留，多半是早先留下的：告诉用户，不用等，用户同意后 release。

**预算。** 记完账再 `ctl auth check --probe ...`（SKILL.md 的第 3 步）。输出里的 `open_session` 应当就是这次开机的那一段；为 null 是账还没记上，判断里缺了这次开机已经用掉的部分，先回去记账。

**定时关机与最晚关机。**

- 这一行已经有定时关机时不取消。实例开着时的定时是给这次开机设的（用户自己设的，或别的对话设的），是唯一的硬上限，在汇报里说一句。它与项目的设置算出的时刻只差一两分钟就不动；差得多，问用户要不要改，不自己把它往后推。这一行没有、而用户选了控制台定时关机的，照第 8 节设。
- 按"每次开机"算的时长（最晚关机"每次开机最多 N 小时"、定时关机"每次开机后 N 小时"）从 `booted_at` 算起，剩下的是 N 减去已经开了的时间（`ctl now` 的输出减 `booted_at`），用命令算。已经不剩时不自己重新起算，问用户。
- 接手时 deploy 或 arm 不成：这台实例不是你开的机，上面可能有用户自己的东西。不跑任务，把报错告诉用户，关不关由用户定；不照"开机后 deploy 或 arm 不成"那一行自己关机。
- 接手别的对话配置过的开机（用户同意后 `arm --rearm`）会整个替换原来的配置。问用户时把它设的最晚关机说出来（`ctl status` 的 `deadline_in_s`），用户没有另外的指示就保留，写成 `--deadline <deadline_in_s>s`（要带 s，纯数字会被当成分钟）。
